1. Deepen the Section Timestamp Tracker

Strong local-substitutable
static/app.js — handleSectionWordProgress() · triggerSectionRetake() · btnStop handler
static/app.js — parsedSections[] (module-level, mutable plain objects)

Before

Cross-section: one word arrives → 6 call sites mutate parsedSections[]

updateHighlighting(wordIndex)
handleSectionWordProgress(word) — find(), mutate .startSec
triggerSectionRetake() — nulls .startSec, .endSec
btnStop — closes last section, calls stopRecording(sections)
media.js stopRecording — reads .startSec / .endSec
processAudioTakes() — slices by sec timestamps
6 call sites. No interface. Any one can corrupt the slice coordinates passed to processAudioTakes.

After

Deep module: SectionTimeline — one interface, all mutation inside

SectionTimeline
.wordSeen(word, nowSec) → void
.retake(sectionId) → seekIndex
.close(nowSec) → void
.getSectionMarkers() → Section[]
highlight
btnStop
stopRecord

all read via .getSectionMarkers()

One module owns startSec/endSec. 4 methods. Edge cases (re-take reset, partial section) handled internally.

Problem

Section timestamp state scattered across six call sites in app.js; any site can corrupt the slice coordinates passed to processAudioTakes.

Solution

Extract SectionTimeline owning all mutation of startSec/endSec behind a 4-method interface.

Wins

  • • locality: timestamp bugs concentrate in one module
  • • interface shrinks: 4 methods vs 6 mutation sites
  • • leverage: retake logic tested once, not per-caller
  • • deletion test passes: removing it concentrates complexity

2. Collapse the stopRecording Encoding Pipeline

Strong local-substitutable
static/media.js — MediaSession.stopRecording() · onstop handler (lines 903–1007 — 104 lines)

Before — interface nearly as tall as implementation

interface

stopRecording(opts)

impl

onstop handler

onstop does everything:

• format detection

• decodeAudioData + 2s timeout race

• WAV/MP3 encode branch

• processAudioTakes()

• filename generation

• 3× fallback paths

• 2.5s safety timer

~104 lines, untestable in isolation

After — shallow onstop, deep RecordingFinalizer

interface

finalizeRecording(chunks, opts)

impl

RecordingFinalizer

onstop becomes 8 lines:

clearTimeout(timer)

resolve(await

 finalizeRecording(chunks, opts))

RecordingFinalizer owns:

• decode + timeout

• encode dispatch

• take slicing

• all fallback logic

Node-testable with fake AudioBuffer

Problem

The onstop closure is 104 lines of sequential mutation bound to a live MediaRecorder. No part of it is testable without a real browser.

Solution

Extract RecordingFinalizer: finalizeRecording(chunks, opts) → TakeSet. onstop becomes a thin adapter.

Wins

  • • interface shrinks: one call vs 104-line closure
  • • locality: encoding bugs concentrate in RecordingFinalizer
  • • leverage: testable with fake AudioBuffer in Node
  • • two adapters: real MediaRecorder + test fixture justify seam

3. Seal the Save-to-Disk Seam

Strong ports & adapters
static/app.js — saveTakeToDisk() · blobToBase64() · takeSavedListeners[]
session.py — PrompterSession.save_take() · server.py — WebSocket dispatch("save_take")

Before — 4-hop base64 round-trip

flowchart TD
  A["btn-save-disk"] --> B["blobToBase64()"]
  B --> C["send save_take over WebSocket"]
  C --> D["session.py: b64decode + write"]
  D --> E["emit take_saved"]
  E --> F["takeSavedListeners + 10s timeout"]
  classDef leak stroke:#dc2626,stroke-width:2px;
  class C,F leak

• Server caps WebSocket at 2 MB — silently truncates video
• base64 bloats blob by 33% in memory
• 10s timeout is the only error signal

After — LocalFileSaver with two adapters

flowchart TD
  A["btn-save-disk"] --> B["LocalFileSaver.save(blob,filename)"]
  B --> C{showSaveFilePicker?}
  C -- yes --> D["File System Access API — zero server round-trip"]
  C -- no --> E["HTTP POST /save — streaming multipart"]
  E --> F["server.py: shutil.copyfileobj to recordings/"]
  classDef deep stroke:#6366f1,stroke-width:2.5px;
  class B deep

• No base64. No 2 MB cap. No timeout promise.
• Two real adapters justify the seam.

Problem

Saving a take base64-encodes the entire blob, sends it over a 2 MB-capped WebSocket, and waits on a hand-rolled 10s timeout — three independent failure modes that silently eat large video files.

Solution

Extract LocalFileSaver: prefer showSaveFilePicker (zero server round-trip), fall back to streaming HTTP POST. No base64. No cap. No timeout.

Wins

  • • locality: all save paths in one module
  • • leverage: eliminates FileReader, base64, timeout, listeners
  • • interface shrinks: save(blob, filename) → Promise<bool>
  • • two adapters: File System Access + HTTP POST justify seam
  • • deletion test: removing takeSavedListeners[] concentrates complexity
Note: docs/session_recording_lifecycle.md describes the base64/WebSocket flow as a feature. Adopting the HTTP POST adapter revises that — worth a quick doc update once the seam is established.

4. Concentrate the Export Review Modal State

Worth exploring local-substitutable
static/app.js — openExportModal() · closeExportModal() · currentExportTakes[] · activeModalObjectUrls[]

Before — interface nearly as wide as implementation

interface

openExportModal(takes,mode,fmt)

impl

openExportModal does:

• revokes old blob URLs

• creates new blob URLs

• mutates currentExportTakes (module scope)

• innerHTML injection

• registers 3 listener sets per open()

• hides/shows batch buttons

Listeners capture stale takes[] from closure on each open

After — deep ExportSession module

ExportSession
.open(takes, mode, fmt) → void
.close() → void
.saveOne(idx) → Promise<bool>
.saveAll() → Promise<void>
.downloadZip() → Promise<void>
Listeners wired once on construction, not per open().
currentExportTakes and activeModalObjectUrls live inside the module.

Problem

The Export Review modal is shallow: openExportModal is nearly as complex as its implementation. Three listener sets registered per open. State leaks across module scope.

Solution

Extract ExportSession: constructor wires listeners once; open() updates internal state and refreshes DOM only. Blob URL lifecycle owned by the module.

Wins

  • • interface shrinks: 5 methods replaces 125-line function
  • • locality: object URL leaks concentrate in one module
  • • leverage: listener dedup removes double-fire risk

6. Extend Dual-Layer Export to the Video Path

Worth exploring in-process
static/media.js — MediaSession.stopRecording() video fallback path (lines 972–984)

Before — video path silently ignores sections[]

sequenceDiagram
  participant app as app.js
  participant ms as MediaSession
  app->>ms: stopRecording({sections, dur})
  Note over ms: isAudioOnly = false (video mode)
  ms-->>app: {blob, takes:[masterOnly]}
  Note over app: sections[] never consumed
  Note over app: Export modal: 1 file only

After — section timestamps surfaced in modal

sequenceDiagram
  participant app as app.js
  participant fin as RecordingFinalizer
  app->>fin: finalize(chunks,{sections,'webm'})
  fin-->>app: {master, sectionMarkers[]}
  Note over app: ExportSession shows master +
  Note over app: section times for Resolve cuts

Problem

sections[] is passed to stopRecording in video mode but silently ignored — the fallback always returns one master blob, breaking the dual-layer export promise for video.

Solution

Surface section timestamps as metadata in the Export Review modal ("Section [Intro]: 0:00 – 0:43"). Full video slicing can follow; the timestamps alone give DaVinci Resolve users the cut points they need.

Wins

  • • locality: video path explicitly handles or explains sections
  • • leverage: section metadata = Resolve-ready cut points
  • • interface: stopRecording contract consistent across modes

Top recommendation

Start with Candidate 3 — Seal the Save-to-Disk Seam

The base64/WebSocket delivery path is the most immediate production risk: the server hard-caps WebSocket messages at 2 MB, silently truncating any video take; the 10-second timeout is the only error signal; and the hand-rolled takeSavedListeners[] array is a concurrency accident. Extracting LocalFileSaver with showSaveFilePicker → HTTP POST fallback eliminates the cap, the base64 overhead, and the timeout — and it establishes a clean seam testable against both adapters independently. Everything downstream — the Export Review modal (C4) and dual-layer video export (C6) — gets simpler once this save seam is solid.
